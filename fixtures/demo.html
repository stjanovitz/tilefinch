PSP Pocket Web

This desktop laboratory tests a memory-capped engine shaped for a 480 by 272 handheld screen. Parsing, scripting, layout and painting share one explicit allocation budget.

Deferred by design

Only visible RGB565 tiles are rasterized. A retained display list lets the cache discard distant pixels and rebuild them when scrolling returns.

  • HTML arrives in small chunks.
  • Text wraps inside the viewport.
  • JavaScript has a separate heap ceiling.
  • Tile eviction is expected, not exceptional.

Modern language core

The embedded script uses optional chaining, const bindings, arrow functions, template strings and Array methods. Those features run in QuickJS rather than a legacy ES5 interpreter.

Long-page checkpoint A

Browser tiling controls raster memory, but it does not make the DOM, computed styles, layout boxes or JavaScript heap disappear. Those structures need their own quotas and future fragmentation strategy.

The proof of concept measures that distinction directly.

Long-page checkpoint B

A PSP implementation can prioritize input, visible painting, visible resource decode, parsing, scripts and finally near-viewport prefetch. Work outside the viewport must be cancellable.

Complex tables, floats, Grid and geometry queries will sometimes force a synchronous layout expansion. Those are explicit compatibility costs.

Long-page checkpoint C

Stage two should port only the tile compositor and scheduler to real hardware. Networking, full CSS and a DOM bridge come after memory and scroll behavior are proven on the device.

The architectural question is whether useful pages can remain controlled under the PSP memory ceiling, not whether a desktop engine can merely be cross-compiled.
